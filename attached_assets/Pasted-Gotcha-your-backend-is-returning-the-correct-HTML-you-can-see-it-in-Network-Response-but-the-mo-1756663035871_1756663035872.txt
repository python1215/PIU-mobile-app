Gotcha—your backend is returning the correct HTML (you can see it in Network → Response), but the modal stays stuck/spinning because of a few front-end wiring issues in the template. Here are the concrete problems I can see in the files you shared, plus the minimal fixes:

# What’s actually going wrong

1. ### Scripts inside the HTMX response won’t run

Your HTMX response (the contract list fragment) previously shipped a `<script>…selectContract()…</script>` and the contract “Select” buttons call `onclick="selectContract('…')"` from inside the swapped content. HTMX does **not** execute scripts it swaps into the page, so those `onclick` handlers end up calling an **undefined** function. That looks like a “frozen” modal after the list appears.
Fix: keep `selectContract()` in the main page template (not inside the HTMX fragment). You’ve already moved it into the page in your latest file (good): see the bottom where `function selectContract(contractRef) { … }` is declared in the full template, outside the HTMX content  / .

2. ### Mixed/duplicate modal open strategies (race & “stuck spinner”)

Across the uploaded versions of the same template, the “Select Contract” button sometimes has `data-bs-toggle="modal"`/`data-bs-target="#contractSelectionModal"` **and** also opens the modal programmatically after HTMX swaps content. This inconsistency can open an **empty** modal first (showing only the spinner) and then the swap may target a *different* instance or be prevented by an exception, which looks like “freeze”.
You can see one copy of the button **with** `data-bs-*` attributes  and other copies **without** them (HTMX-only)  / .
Fix: use **one** approach. The reliable pattern is:

* Do **not** put `data-bs-toggle/target` on the button.
* Let HTMX load the list into `#contractModalBody` and then call `bootstrap.Modal.getOrCreateInstance(modalEl).show()` on `htmx:afterSwap`. That’s exactly what your script already does here: it listens on the **target element** (`#contractModalBody`) and opens the modal once the content has been swapped  / .

3. ### Event listeners bound on the wrong element (in some copies)

HTMX fires `htmx:afterSwap` on the **target** element (the node receiving the HTML). In a few variants of your template, handlers were attached to the **button** instead of the **target** for before/after events. That means your code wouldn’t run at the right time, and the modal never opens with the loaded content.
Fix: make sure the listeners are on `#contractModalBody` (not the button). Your good copy does exactly that: `modalBody.addEventListener('htmx:afterSwap', …)` and `modalBody.addEventListener('htmx:beforeRequest', …)` .

4. ### Possible duplicate IDs on the page

Because multiple versions of the modal markup show up across your file uploads, it’s easy to end up with **more than one** `#contractSelectionModal` / `#contractModalBody` in the DOM. Bootstrap & HTMX will interact with the *first* one they find, while you’re looking at another—classic “request succeeded, UI didn’t change” symptom.
Fix: ensure there is **exactly one** modal with `id="contractSelectionModal"` and **exactly one** `id="contractModalBody"` on the page. (Your latest template has a single modal scaffold at the bottom, which is correct) .

# Minimal working pattern (what to keep)

* The button with HTMX only (no Bootstrap data attributes):
  `hx-get` to your view, `hx-target="#contractModalBody"`, `hx-vals` (or `hx-include`) to send `project_id` and `contract_type` .
* A single modal in the page with an empty `#contractModalBody` placeholder .
* JS that:
  a) shows a spinner on `htmx:beforeRequest`,
  b) opens the modal **after** the content is swapped (`htmx:afterSwap`),
  c) defines `selectContract()` globally in the page (not in the HTMX fragment) so the “Select” buttons inside the swapped list can call it. See lines for (a) and (b) here  and the global function here .
