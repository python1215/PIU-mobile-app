# Likely blockers (and how to fix)

1. You’re hand-building several `<select>`s instead of rendering the bound widgets

* Fields: `projectID`, `compID`, `subcompID`, `activityID`. In the template you create raw `<select>` tags and loop `for choice in form.projectID` to print `choice.tag`. That’s valid, but very easy to misalign with the bound form state (required flags, widget attrs, selected values, etc.).
  **Fix**: As a sanity check, temporarily render these as the actual widgets to rule out binding issues:

```django
{{ form.projectID }}
{{ form.compID }}
{{ form.subcompID }}
{{ form.activityID }}
```

If saving suddenly works, the custom `<select>` markup is the culprit (missing attributes). Then re-introduce your custom HTML carefully (keep the exact `name` attr, keep the bound options, and add `required` if the field is required).

2. Client-side validation may be blocking submit
   You add `novalidate` and your JS prevents submission when `form.checkValidity() === false`. Because your custom controls don’t include `required`, the browser might be flagging other issues (e.g., invalid date/number types coming from the custom controls).
   **Fix**:

* Add `required` to the required fields (the ones marked with the red asterisk), e.g.:

```html
<select ... required>
<input ... required>
```

* Or comment out the whole validation IIFE to confirm submit isn’t being stopped in the browser.

3. `loginUser` required but never set in the view
   Your table shows `loginUser_id` always populated. If that column is `NOT NULL`, saving without assigning `obj.loginUser = request.user` will raise an integrity error and nothing will be saved.
   **Fix** (in your view handling POST):

```python
form = ContractProfilingWorksForm(request.POST, request.FILES)
if form.is_valid():
    obj = form.save(commit=False)
    obj.loginUser = request.user  # IMPORTANT
    obj.save()
    form.save_m2m()
else:
    print(form.errors)  # and re-render the same template with errors
```

If you’re already doing this, surface `form.errors` in the template (you do render field errors, but also log/print `form.errors` server-side to see hidden issues).

4. Capitalized field names (`Latitude`, `Longitude`)
   Your template uses `{{ form.Latitude }}` and `{{ form.Longitude }}` (capitalized). Django normally expects lowercase field names. If your model field names are lowercased (`latitude`, `longitude`), the form fields will also be lowercased—referencing capitalized names in the template will render nothing, so the POST won’t include those values and validation may fail.
   **Fix**: Ensure the template field names exactly match the form fields (`{{ form.latitude }}`, `{{ form.longitude }}`), or keep the model/form fields capitalized consistently.

5. Mismatched widget types for numeric/date fields
   Columns like `contract_value` (Decimal), `gross_floor_area_m2` (numeric), `Latitude`/`Longitude` (float), and dates must parse cleanly. If your widgets are plain text inputs and the user types commas or non-numeric text, form validation will fail.
   **Fix**: In the form, ensure numeric and date widgets/types are correct, or add `inputmode`/`type` to HTML:

```html
{{ form.contract_value|add_class:"form-control" }}
<!-- Or explicitly: -->
<input type="number" step="0.01" name="contract_value" ...>
```

Likewise for dates; ensure the widget matches the format the form expects.

6. Required fields missing the `required` attribute in the custom markup
   You visually mark some fields as required (red asterisk) but the actual `<input>`/`<select>` lacks `required`. That means the browser can allow empty posts, but the Django form will then fail server-side (and you’ll only see it if you re-render the page with errors).
   **Fix**: Add `required` to those inputs/selects, or rely on rendering the form widgets directly (Django will add the `required` attribute if the field is required).

7. HTMX cascading selects don’t affect saving, but can hide validation problems
   Your `hx-get` chains (`load_project_components`, etc.) are fine for populating options, but they don’t run on POST. If the user hasn’t actually chosen a value after the cascade, the selected value might still be blank → server-side required validation fails.
   **Fix**: Make sure each dropdown actually has a non-blank selection before submitting (add `required`). Also surface errors next to those selects (you already do, which is good).
